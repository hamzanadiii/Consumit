# External player REA investigation — 2026-10-18

The strongest observed example is VidRift: its movie player decoded and advanced in an isolated browser and displayed movie footage inside production Consumit Watch. VidCore's document returned a Cloudflare 403 in this environment; adding the configured fallback does not establish working playback. Consumit already has the core controls and recovery machinery needed for a strong owned player. The useful next work is clearer discovery, less control density on phones, and measured provider quality rather than a new visual theme.

Captures straddled midnight on October 17–18. ## How the observed players work

**VidRift — observed:** a compact dedicated page loads one approximately 169 KB application script and approximately 617 KB Hls.js asset. It fetches video and audio initialization objects through its own API and signed fragmented MP4 chunks from an external CDN. The UI exposes provider names Orion/Vela/Atlas/Titan/Lyra, language-specific sources, quality, audio/subtitles, subtitle upload/sync/customization, volume boost, size modes, lock, PiP, cast, and skip intro. Intro metadata and a source-success reporting endpoint were requested. Available controls do not prove every listed capability worked.

**VidRift — source observation/inference:** the public wrapper contains local preference storage, HLS integration, media-event handling, requestVideoFrameCallback use, and parent postMessage calls. These are implementation candidates corroborated partly by runtime playback, not proof of its complete retry policy. A declared event channel is an opportunity to investigate; Consumit does not currently trust it for progress.

**Vixsrc — observed:** the outer Next.js route obtains title data and loads a nested player document. That document uses JWPlayer, its HLS provider and a small skin wrapper. The captured wrapper registers play, pause, seek and time updates and emits `PLAYER_EVENT` messages to its parent with wildcard destination. Unknown: whether the outer page forwards these reliably to Consumit, exact canonical ID mapping, long-play reliability, or stable protocol guarantees. The general-purpose engine plus small wrapper is a useful separation pattern; its presence alone does not prove superior recovery.

**Consumit — established source and runtime:** direct/relay sources already feed the owned player through adapters. Watch owns selection, recovery and canonical identity; member progress is independent. The code already has decoded-first-frame startup deadlines, seeking/stall detection, cancellation/generation guards, semantic quality/audio preferences, subtitle tooling and mobile panels. Do not reimplement those as if missing. External frames retain the ADR 0006 boundary: iframe load is not playback success; progress sync and automatic next episode remain unavailable.

## Prioritized improvements within the current design

1. **Improve source discovery:** keep Consumit Server and External players separate; make both groups reachable without a long scroll and keep provider names readable. Avoid raw implementation IDs duplicating human labels in member menus. Preserve Admin order, current selection, favorites and keyboard focus. Use the existing flat rows and tokens.
2. **Reduce phone control density:** retain Play, seek, sound, source and fullscreen prominence; use the existing Settings panel for secondary utilities, keeping captions easy to reach. Verify portrait/landscape, safe areas, keyboard focus and coarse-pointer targets. Preserve the Cinema After Midnight palette, artwork preparation and current player geometry.
3. **Compare providers using the existing instrumentation:** Watch already forwards playback events and Admin ProviderBench already records startup, decoded frames, stalls and seeking. Extend that evidence only where needed for comparable provider/delivery summaries, such as resolution-to-ready versus ready-to-decoded-frame, seek-to-resume and fallback reason. Label ready versus playing versus blocked distinctly. Existing first-frame/stall/cancellation behavior and native telemetry are foundations, not missing features. Compare p50/p95 across regions and representative movie/series/anime samples before adjusting timeouts; external playback remains unmeasured without a reviewed event protocol.
4. **Investigate a narrowly reviewed external event adapter:** begin with read-only diagnostic events for VidRift/Vixsrc. Before any acceptance, require exact `event.source === iframe.contentWindow`, exact configured `event.origin`, schema/type/size validation, finite monotonic bounds, rate limits, canonical title/episode binding and stale-instance rejection. Test malformed, cross-origin and replayed events. Do not infer trusted viewing history from wildcard messages or silently enable progress/auto-next; those need an explicit ADR amendment and protocol evidence.
5. **Make subtitle/source state calmer and testable:** retain the existing subtitle browser and semantic preferences, expose active language/quality in the established panel, and verify hidden menus are inert and omitted from accessibility navigation. VidRift demonstrates discoverable feature grouping; its feature inventory should not create duplicate Consumit controls.

These are recommendations, not a deployed redesign. Provider roster deployment acceptance is documented separately in [external-player-roster-2026-10-18.md](./external-player-roster-2026-10-18.md). VidCore's block cannot be fixed by changing Consumit's CSS or accepting its URL. No claims are made about DRM, every subtitle, casting, television navigation, complete upstream architecture, ads over long sessions, or availability in other browsers/regions.
