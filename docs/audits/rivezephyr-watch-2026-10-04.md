# RiveZephyr Watch versus Admin

The member reported RiveZephyr playing in Admin and PROVE but failing in the normal Consumit Player, most recently Game of Thrones. The live repro drives the deployed Watch screen, pins RiveZephyr, intercepts progress/event writes and records only sanitized provider/status/media metadata. Movie 550 initially selected RiveZephyr with 200, then received three relay 403s and fell back to Miami. The first harness accidentally treated that fallback's decoded frames as success; its final assertion also requires the selected provider to remain RiveZephyr and no failed relay media requests. Game of Thrones S1E1 initially returned 503 on selection while the fresh configured adapter resolved its source.

Ranked explanations were a different selected rendition, a stale source and differing relay hints/grants. Fresh configured resolution for both references produced one validated Zephyr source on `zcdn.bluevelvet.space` with the same Referer, Origin and User-Agent hints. No source order or header change was needed. A counterfactual changed only grant lifetime for that same source: 90,000ms returned a valid manifest with 200, 1,800,000ms returned 403, and 1,795,000 / 1,770,000 / 1,740,000ms all returned valid manifests with 200. This reproduced the Admin/Watch difference for movie 550 and series 1399 S1E1.

Watch used the exact thirty-minute maximum for estimated-expiry relay sources. The Worker rejects capabilities whose expiry lies more than thirty minutes after its own current time. A slightly slower edge clock therefore rejects a freshly issued maximum-length grant. Admin uses a ninety-second preview grant and avoids that boundary. Watch now reserves five seconds below the maximum, for both estimated and known long-lived relay sources, and publishes the actual cutoff consistently in session and grant. Direct expiry behavior and the strict edge checks remain intact. No provider policy, headers, Worker deployment, subscription, stored provider settings or web code changed.

The new regression fails with `Invalid grant` before the fix when opening a Watch-issued grant against an edge clock two seconds behind. It passes after the fix for estimated and known source expiries, and verifies the public cutoff equals the authenticated cutoff and expiry is still rejected. Eighty-seven playback/resolver/delivery/Worker checks pass. Full API TypeScript and changed-code lint pass.

The source-mounted API is restarted. Real desktop Chrome playback now remains on RiveZephyr for Game of Thrones S1E1 and Fight Club, with all recorded manifests/init/media responses at HTTP 200 and no page errors or provider fallback. In a fresh browser profile, the usual Play button was clicked when autoplay remained paused; this avoids confusing browser autoplay permission with failed source delivery. Game of Thrones advances to 10.63 seconds with 259 decoded frames at 3840×2160; Fight Club advances to 10.19 seconds with 249 frames at 3840×2160. Both adapt from an initial 720p rendition through the real HLS master.

This checks startup and short continuous playback on the two references, not a full-title endurance run or all episodes/regions/browsers. Old immutable grants keep their original expiry; starting a new Watch session gets the repaired grant. The bounded five-second reserve covers modest clock differences rather than weakening the maximum-lifetime validator.
