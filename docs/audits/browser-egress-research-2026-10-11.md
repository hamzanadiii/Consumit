# Browser lookup and zero-server-media delivery — 2026-10-11

## Finding

Viewer-side lookup is a plausible way to avoid both another VPS and relay video traffic: issue the link on the viewer's connection, then play on that connection. It is feasible for an ordinary website only when every lookup response needed by the adapter is readable from the production origin, and the resulting media graph is playable from that browser. Successful SDK resolution on the developer's Windows machine does **not** establish browser Fetch compatibility. Fresh actual Chrome checks find the initial Vixsrc and LookMovie lookup responses unreadable from the production origin under both no-referrer and legitimate origin-referrer policies. This ordinary-website lookup route is presently not viable for either checked endpoint.

Vixsrc publishes a separate solution: its supported external player can avoid OVH lookup entirely. An isolated plain-iframe Chrome check decodes both movie and series samples with no app-server video relay. It remains an **Embed** using provider controls, and requires a separately reviewed relaxation of the current frame sandbox. Its published protocol does not export a media URL to the Consumit Player; playback messages have not been accepted in the live check. This is a research result, not a completed new production route.

## Evidence already measured

The [production parity audit](./provider-production-parity-2026-10-10.md) separates resolution from playback. Vixsrc rejects the tested OVH API/page requests with a 403 challenge, while developer-network SDK resolution and production-origin Chrome playback succeed for sampled movie/series sources. The developer-issued root also receives 403 when fetched on OVH; this establishes location-dependent rejection, not universal IP binding.

LookMovie's paired exact-link check shows opposite outcomes: an OVH-issued link returns HLS with allowed-origin `*` on OVH and eleven non-media bytes on Windows; a Windows-issued link shows the reverse. Adding the production Origin changes neither result. The ignored sanitized report is `local/production-playback/lookmovie-egress-ovh-report.json`. This strongly supports egress-dependent delivery for the checked links, consistent with IP binding. Its precise upstream implementation is unknown. [ADR 0008](../adr/0008-provider-egress-and-media-routing.md) and the [OVH delivery audit](./ovh-media-relay-2026-10-11.md) record the bounded same-egress LookMovie fallback already deployed.

## Browser rules that constrain the design

An ordinary script cannot set arbitrary `Origin`, `Referer`, `Host` or `Cookie` request headers. Cross-origin Fetch requires the remote response's CORS permission; `no-cors` exposes an opaque response with no readable headers/body. A caller-supplied referrer from another origin does not impersonate that site. Service workers use the same Fetch model, so adding one cannot turn unreadable upstream responses into readable lookup JSON/HTML. [Fetch Standard](https://fetch.spec.whatwg.org/#forbidden-request-header), [opaque responses](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque), [Request construction](https://fetch.spec.whatwg.org/#dom-request).

A service worker can cache or synthesize responses, but synthesis requires bytes it already has. It does not grant a website the browser-extension permissions needed for unrestricted cross-origin network access. [Service worker fetch events](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/fetch_event).

Cross-origin framing does not let Consumit read the provider frame's DOM or JavaScript state. Communication requires code in the other frame to send supported messages. Check both `event.origin` and `event.source`, validate bounded message data, and target an exact recipient origin when sending. [Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy), [postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage).

Browser extensions are a distinct installable product. Chrome allows an extension service worker or extension page to fetch explicitly permitted remote hosts, while content-script Fetch retains the page's cross-origin restrictions. Such an extension could perform viewer-side lookup, but installation, host permissions, distribution, supported-browser coverage and ongoing maintenance are new requirements; it is not a transparent fix for ordinary visitors. Upstream blocking and media compatibility would still need measurement. [Chrome extension network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests), [permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions).

The shipped [Vixsrc adapter](../../packages/provider-sdk/src/adapters/vixsrc.ts) requests `/api/movie/{id}` or `/api/tv/{id}/{season}/{episode}`, accepts a same-provider `src` page, parses bounded source token/expiry/playlist information, and validates HLS. The [LookMovie adapter](../../packages/provider-sdk/src/adapters/lookmovie.ts) searches `lmscript.xyz/v1/movies`, matches title/year, and reads `/v1/movies/view?expand=streams,subtitles&id=…`; current movie-only support and validation remain relevant.

## The supported Vixsrc Embed alternative

Vixsrc's own documentation publishes `/movie/{id}` and `/tv/{id}/{season}/{episode}` embed URLs, plus `autoplay`, `startAt` and audio `lang` parameters. It documents `PLAYER_EVENT` messages carrying `play`, `pause`, `seeked`, `ended` or `timeupdate`, with `currentTime`, `duration` and `video_id`. This could support a narrowly reviewed progress bridge after actual movie/episode event checks. It does not document commands for Consumit-owned playback controls or export of signed media URLs. Its custom-domain marketing is not evidence that the underlying media becomes browser-compatible. [Vixsrc documentation](https://vixsrc.to/).

Consumit's [ProviderFrame](../../apps/web/src/app/shared/provider-frame.tsx) currently advertises no progress sync and listens only for frame document load/error. [ADR 0006](../adr/0006-provider-embed-fallback.md) explicitly conditions progress integration on a reviewed playback-event protocol. A future Vixsrc bridge must remain provider-scoped: exact configured URL, exact frame origin/source, canonical title and episode context, plausible finite duration/currentTime, event allowlist, throttled progress, and no raw upstream URL acceptance. Movie `video_id` may not uniquely establish a TV episode; episode correspondence must be measured. An iframe load alone must never count as decoded playback.

The generic shipped frame adapter also fetches pages from the server as a liveness gate. Reusing that gate for Vixsrc would reproduce OVH's rejection. A browser-only canonical Vixsrc frame candidate needs an explicit reviewed resolution-state distinction and browser failure handling, rather than calling an unchecked frame successfully playback-checked. No shared frame contract or policy was changed in this research.

## Redirects, native video, stale sources and address families

A redirect to an upstream media URL leaves the final media request on the viewer's connection; it does not make that request originate from the resolving server. A provider-supported redirect endpoint that *itself* issues a playable link on the viewer's request could be useful, but neither shipped recipe is such an endpoint: one consumes JSON plus HTML, the other JSON. There is no evidence that inserting a redirect in our API changes upstream issuance.

Native video can sometimes consume media without JavaScript reading its bytes when `crossorigin` is absent. That does not parse a provider's JSON/HTML lookup response, and it cannot make eleven denied bytes into valid media. Native HLS is browser-dependent; the owned hls.js path requires CORS on all required resources. Changing engines may help a pure-CORS media sample, but not the measured LookMovie body failure or Vixsrc lookup challenge. [Video element](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video), [hls.js CORS requirements](https://github.com/video-dev/hls.js#cors).

DNS rotation, IPv4 versus IPv6, cache age, redirects and expiring signatures are possible confounders in general. Existing paired LookMovie checks reused each exact fresh signed URL on both connections and controlled Origin, then sampled graph media, which is stronger than comparing unrelated titles/hosts. This justifies the observed egress-dependent conclusion; it does not identify the provider's internal binding algorithm. A viewer-side route still needs lookup/media to use compatible address families, and must re-resolve after network changes rather than reusing an IP-bound source across Wi-Fi/mobile transitions. No raw IP, token or signed URL is needed in saved reports.

## Smallest no-new-subscription validation

1. On a real production-origin browser page, Fetch the fixed Vixsrc API and LookMovie catalog with `mode: cors`, `credentials: omit`, only safelisted Accept, and `referrerPolicy: no-referrer`. Do not execute upstream page scripts or set forbidden headers. Retain only status, response type, bounded schema result and safe host classification.
2. If readable, verify the remaining exact adapter hops and bounded schema, keeping signed URLs only in memory. Initial catalog CORS permission does not prove stream-issuance CORS permission.
3. For a complete viewer-issued source, test the owned player: decoded video, seek/resume, required audio/subtitle graph, quality switch, fresh issuance/renewal and multiple viewer connections. Do not ship browser resolver support on a one-hop result.
4. Independently test the published Vixsrc iframe as an explicit Embed candidate. Measure playback and messages, inspect sandbox behavior, and preserve honest recovery if the upstream rejects that viewer. This trades provider controls for zero app-server video traffic; it is not Direct playback in the Consumit Player.
5. Keep already working Direct providers and the bounded LookMovie OVH fallback. If browser lookup is blocked and a provider offers no usable integration, there is no demonstrated ordinary-website mechanism that grants the same benefits as a local unrestricted resolver without another accepted execution path.

### Actual production-origin browser lookup measurement

At 2026-10-11 18:13 UTC, Chrome on the real `https://consumit.online/about` page fetched the fixed Vixsrc `/api/movie/550` endpoint and LookMovie's Fight Club catalog query from the developer's connection. CSP and CORS remained active; requests omitted credentials and Referer and sent only a safelisted JSON Accept value. Both readable-CORS attempts failed, with one Chrome CORS-policy diagnostic for each. Both `no-cors` controls returned an opaque response, status zero and zero readable bytes. Subsequent issuance/page hops were not attempted after the initial gate failed. The sanitized ignored artifact is `local/production-playback/browser-lookup-cors-report.json`.

The same probes were repeated at 18:19 UTC with `referrerPolicy: origin`, letting the browser send the legitimate production-origin Referer. Both initial lookup responses still fail readable CORS; both opaque controls still expose zero bytes. The second sanitized artifact is `local/production-playback/browser-lookup-origin-cors-report.json`. These failures make ordinary website resolution presently unusable for the checked recipe endpoints under both legitimate policies. The result is origin/network/time-specific, not a claim that every endpoint or future provider integration is blocked. No extension, home agent, third-party host mutation or new paid service was installed.

### Actual published-player browser measurement

Chrome tested the documented Vixsrc movie-550 and series-1396 S1E1 frames from the production-origin page, using Consumit's existing standard frame sandbox. The no-referrer attempt is preserved separately and the screenshot shows a provider error explicitly rejecting that policy. A corrected `referrerPolicy: origin` attempt loads provider documents with HTTP 200, but both movie/series expose no video and send no validated playback messages. A first diagnostic `sandboxRefusal` flag incorrectly searched script text as well as rendered text; it is not evidence of a visible refusal. The preserved origin movie screenshot is black, so the narrower observation is no decoded video with that tested policy.

At 18:22 UTC, fresh isolated Chrome contexts loaded the same published URLs with origin Referer and **no sandbox attribute**. Both movie 550 and series 1396 S1E1 decoded 1280×720 video, started at the requested 60 seconds and advanced beyond 64 seconds unpaused. A corrected repeat at 18:23 UTC reproduces both successes, advances to roughly 64.6 seconds, and finds no rendered sandbox-refusal marker. The latest sanitized artifact is `local/production-playback/vixsrc-embed-browser-report.json`; the earlier no-referrer artifact remains `local/production-playback/vixsrc-embed-no-referrer-report.json`. No validated `PLAYER_EVENT` was accepted during these short tests. These are actual playback samples, not full-duration, all-browser, all-network, cast or progress-sync certification. The frame-policy diagnostic has no production registration or saved-provider changes, and supplies no media URL to Consumit's native player.

A corrected standard-sandbox movie control at 18:24 UTC again returns provider documents with HTTP 200, but remains without video for the 35-second observation and classifies rendered `innerText` as a sandbox-refusal marker. Its separate artifact is `local/production-playback/vixsrc-embed-sandbox-report.json`. This controlled difference supports the provider-scoped frame-policy incompatibility; the earlier script-text flag is not used as proof.

Removing the sandbox also removes its popup and top-window-navigation restrictions. No popup was observed during this short sample, which does not establish that future playback is free of popups or navigation. The project's existing MegaPlay/VsEmbed exception supplies a review pattern, not automatic permission to weaken every provider frame. Keep any proposed Vixsrc exception exact-provider/host scoped and preserve honest progress limitations until its protocol works in a reviewed test.

The shipped ProviderFrame already sets `strict-origin-when-cross-origin` on the iframe, which sends the origin for cross-origin HTTPS. Watch's no-referrer media correction therefore does not imply that every provider frame loses its Referer. A separately scoped frame-policy diagnostic, if performed, is distinct from silently weakening every frame or changing production.

If the browser path passes, the implementation still needs a reviewed session admission seam. Client-reported URLs are hostile; bind an allowed adapter, canonical title/episode, finite expiry and reviewed HTTPS host/path scope to the session. Do not accept arbitrary media URLs or use client output to expand a relay allowlist. Server-side fetch verification may reproduce an IP-bound failure, so browser delivery evidence must be kept distinct from server verification rather than weakening global provider validation. This report proposes that review boundary; it does not design or implement the contract.
