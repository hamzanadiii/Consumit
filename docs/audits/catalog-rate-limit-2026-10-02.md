# Catalog request-budget repair — 2026-10-02

The member reported catalog failures across pages, most often anime. The job is opening Home, catalog, title, and Watch pages reliably within the existing desktop design.

The live reproduction made bounded reads of an already cached anime from the web container, then opened an anime Watch page. It returned 13 successful reads and 88 responses with status 429. The next metadata request returned `RATE_LIMITED`, limit 100, remaining 0, and `Retry-After: 28`; the Watch render displayed “The catalog missed its cue.” Direct gateway reads of those same anime returned 200. This established the local API bucket as the reproduced cause, rather than an upstream AniList quota or Wi-Fi failure. The existing failure screen labelled every retryable error as a timeout.

Public catalog GETs now use a separate bounded 600/minute bucket. General member requests keep 100/minute and credential routes keep their existing tighter policies. Server-side public metadata uses the existing five-minute Next Data Cache even when consumed by request-bound Home or Watch. Only catalog JSON is shared; metadata fetches carry no member cookie or authorization header, and member/progress/playback endpoints retain their own uncached behavior. No new service, proxy, or paid dependency was introduced.

A second deterministic regression simulated a successful seven-second AniList response. It failed because the web cancelled after six seconds even though the adapter allowed ten. Server metadata reads now have a bounded 12-second deadline. A separate hung-request test verifies that the deadline still fails honestly. This does not guarantee success during an upstream outage or indefinitely queued upstream requests.

Regression tests went red before the repair for metadata fan-out above 100 reads, the missing shared-data-cache policy, premature cancellation, and misleading rate-limit copy. Tests cover the 600/minute boundary across movie/series and anime routes, separate member budgets, session isolation, public-only fetch headers, successful slow responses, bounded hung requests, error-code preservation, and retry copy. All 35 relevant API tests and 15 relevant web tests passed. Web type checking, focused API limiter type checking, changed-file lint, API bundling, and the optimized web image build passed. API-wide type checking still reports existing retired-social contract and private-visibility mismatches outside this slice; it is not claimed as passing.

The API was restarted and the web image rebuilt/recreated. Repeating the original live sequence returned 101/101 successful metadata reads, the next title request returned 200, and the Watch page no longer showed the error. Seven HTTP page samples loaded: Home, Anime browse, anime detail, anime Watch, movie detail, Movies, and Series. Twenty repeated Watch renders returned in 25–91 ms with zero catalog failures and zero extra metadata API reads after warming (the measuring probe is excluded). Desktop Chrome at 1440×900 opened Home, Anime browse, anime detail, and movie detail without catalog failure or page errors. These are local warm-cache measurements, not a cold-network latency guarantee or a load test for multiple instances. Sanitized evidence is in the companion JSON; temporary harnesses were removed after verification.
