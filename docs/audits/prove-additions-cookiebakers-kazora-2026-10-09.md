# PROVE additions: CookieBakers, Kazora, KissKH (direct), VidCoreIO/CineSrc/VidRift Frames (embed), LookMovie LMScript coverage

Date: 2026-10-09. Status: adapters ported, unit-tested, registered, and live-probed; the direct rows are verified CORS-open at the master and the frame rows are verified embed pages behind the shared frame factory.

The member job is resolving more titles through additional configured sources, including anime. Seven items join from PROVE at the owner's request: CookieBakers, Kazora, and KissKH (all direct), the VidCoreIO/CineSrc/VidRift frames (all embed), and LMScript coverage, which resolves through the existing LookMovie adapter rather than a new row.

## What was ported

- `packages/provider-sdk/src/adapters/cookiebakers.ts`: the resolution API `https://stream.lfmx.app/api/stream/cookiebakers/{movie/{tmdbId}|tv/{tmdbId}/{s}/{e}}` returns `{url,duration}`. The route flaps (429/502/504 observed live on first attempts), so the adapter retries up to three times with an 800ms backoff and treats 404 as a genuine miss rather than a flap. PROVE's registry classifies it `direct`; the master sits on a CORS-open CDN (`cookiebakers23blog.xyz`, ACAO `*`), so the row is registered `deliveryMode: 'direct'`.
- `packages/provider-sdk/src/adapters/kazora.ts`: an anime provider keyed directly by AniList id (`ref.id`, `ref.episode`), so it needs no anime title resolver, like Recloud. The watch API returns an embed URL carrying a base64 token with the master plus intro/outro marks in seconds; those are mapped through `parseSkipSegments` into `ProviderSource.skipSegments`. Kazora re-rolls its CDN per call (live probes: `juju`/`kyoo` on the CORS-open `cdnx.aniwatchtv.site`, `kazo` on a `flixcloud.cc` master that 403s, `lufi` on either), so the adapter probes a bounded server cascade and only returns a master that answers as a real CORS-open playlist. Gated CDNs are skipped rather than returned.
- `packages/provider-sdk/src/adapters/kisskh.ts`: a DramaList catalogue matched by title through the server-owned TMDB metadata resolver (like Purstream/LookMovie). The flow searches by title, scores a confident match, looks up the episode (movies are episode 1), mints a community kkey on `enc-dec.app`, then reads the `Video` master from the Episode endpoint. The CDN rotates hosts per title (masters on `hls[N].cdnvideo11.shop`, segments on `hls[N].{verois3|streamingcdn5|newvideostream6|...}.site`, subtitles on `sub.cdnvideo11.shop`), so the adapter verifies each HLS master as a real CORS-open playlist before it becomes a source. Subtitle tracks are direct browser-loadable SRT/VTT on the CORS-open `sub.cdnvideo11.shop` CDN.
- `packages/provider-sdk/src/adapters/frames.ts` gains three TMDB-id embed frames on the existing `createFrameProvider` factory. **VidCoreIO Frame** (`vidcoreioframe`) points at `https://vidcore.io/movie/{tmdbId}` / `tv/{tmdbId}/{s}/{e}` (no `/embed/` prefix) and is live only when the page answers with a `vidcore` marker and at least 10 KB of shell. **CineSrc Frame** (`cinesrcframe`) points at `https://cinesrc.st/embed/movie/{tmdbId}` and `embed/tv/{tmdbId}` — the TV embed carries **no season or episode** because a series picker runs in-frame and the member chooses the exact episode inside the player; it is live only when the page carries the `streaming servers` marker. **VidRift Frame** (`vidriftframe`) uses the standard `https://embed.vidrift.net/embed/movie|tv/...` path but **cannot gate on its page** (it bot-walls datacenter fetches), so the adapter gates through VidRift's keyless subtitle API instead: a `200 WEBVTT` answer for any of six reviewed languages means the title is cataloged and the in-frame lanes will play. None of the three sets a frame-ancestors refusal, so they keep the standard sandbox; none needs a relay approval because they are embed-only and never surface a media URL.
- LookMovie's backend (`lmscript.xyz`) was already covered by the existing `lookmovie` adapter; PROVE's `lmscript` adapter is the same backend. No new row. The one gap was the observed media host `srv315.indismotexclied.cyou`, which the row's `.cyou` shape rule (`^srv[0-9]+\.[a-z-]+\.cyou$`) already admits; the exact host was added to `mediaHosts` in both config files so the allowlist carries it explicitly as well.

## Limits and follow-ups

- CookieBakers' external subtitle catalogue is only reachable through a same-host wrapped-proxy route (`https://stream.lfmx.app/api/subtitles/fetch?url=...`); direct subtitle paths 404. The adapter therefore returns no external subtitles and relies on the HLS master's in-manifest subtitle rendition. If a browser-loadable catalogue host appears, it can be added later.
- Kazora's subtitle media proxy (`kazora.cc/stream-embed/media/...`) answers 403 to any browser `Origin` and sends no CORS header, so it is not browser-loadable. The adapter returns `subtitles: []` and anime captions stay with the first-party subtitle service.
- Kazora's `cdnx.aniwatchtv.site` is the only CORS-open CDN observed; the `flixcloud.cc` and `vault-69` lanes 403 outside the minting session and are skipped. If Kazora rotates to a new open CDN host, the row's `mediaHosts` needs the exact host added.
- CookieBakers flaps on upstream 429/502/504; the three-attempt retry recovers most observed flaps but a fully degraded upstream resolves empty for that title only.
- KissKH's segment CDN rotates per title across `hls[N].{verois3|streamingcdn5|newvideostream5|newvideostream6|streamingvideofaster1}.site`; the `^hls[0-9]+\.[a-z0-9-]+\.site$` pattern covers the family. If a title arrives on a host outside this shape, its playlist segments drop until the pattern widens. Some titles (e.g. The Matrix, The Dark Knight, Interstellar) returned no confident match or no stream in this sample; the adapter reports empty for those rather than guessing.
- The three new frames are embed-only fallbacks: they surface an iframe URL, never a media URL, and the frame source carries no headers, relay recipe, or subtitles (the schema rejects those on iframe sources). Captions stay with the first-party subtitle service. Live probes confirm the VidCoreIO and CineSrc embed pages do not send CORS headers, which is expected and irrelevant for a framed embed.
- CineSrc's TV embed carries no season or episode — a series picker runs in-frame and the member chooses the exact episode inside the player. The frame therefore cannot pin exact episode identity the way the VidCoreIO/VidRift frames (and the reviewed apiplayer/embedapi/vsembed frames) do; that is a real product characteristic of the CineSrc embed, not a porting gap.
- VidRift's gate is catalog presence (its subtitle API answers 200 WEBVTT), not playback evidence; its embed page 403s to datacenter fetches. A cataloged title can still fail to play in-frame if VidRift's own lanes are down, but cataloged is the right precondition for offering the frame.
