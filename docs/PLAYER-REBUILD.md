# Player rebuild evidence

The canary web build uses `NEXT_PUBLIC_PLAYBACK_CORE=next`; the default is `legacy`. Both Watch and public embeds choose the same controller. The first-party media engine remains the single HLS/DASH/native attachment seam, the browser coordinator handles renewal and fallback, and the API owns provider eligibility. The public embed URL, query parameters, and `PLAYER_EVENT` payload stay compatible.

## Controlled baseline and canary

The pre-rebuild legacy Chrome suite passed 9/9 controlled-media scenarios, and the earlier canary Chrome and Firefox suites each passed 9/9. The optimized standalone legacy and canary builds now both pass all 10 production-fixture Chrome scenarios, including native playback and resume, HLS decoding, VixSrc extraction, fallback, paused recovery, subtitle discovery, repeated source renewal, and public embed recovery. Each run uses local deterministic media and cannot establish external-provider performance.

The opt-in benchmark (`PLAYBACK_BENCHMARK=1`) recorded six warm navigation-to-first-video-frame samples for each core in Chromium. Legacy p95 was **2,542 ms** (2,039, 2,093, 2,099, 2,248, 2,378, 2,542); canary p95 was **2,647 ms** (1,634, 1,718, 1,761, 1,888, 2,371, 2,647). The p95 is about 4% slower in this run, so the required 20% improvement is not met. The local Next development server and small sample count make this a screening measurement; repeat in a production-like build before release.

A second development-server run with phase timing swung the other way: legacy p95 **4,893 ms**, canary p95 **3,218 ms**. Legacy `loadstart` occurred 1,648–4,598 ms after navigation, while media `loadstart` to decoded frame took 294–495 ms. Canary `loadstart` occurred 2,189–2,917 ms after navigation, with 258–555 ms from `loadstart` to frame. This variance shows the dev-page startup dominates the measured p95; neither run proves a repeatable 20% production improvement. A production-build benchmark and a larger sample are required for the gate.

The Windows desktop Chrome production-fixture comparison now uses each optimized standalone build, the same local MP4 fixture, and the decoded-frame callback. Two independent batches per core yielded 36 warm samples each after excluding one cold navigation per batch; all 38 starts per core reached a decoded frame. Pooled p50 was **340 ms** for legacy and **340 ms** for canary. Nearest-rank p95 was **637 ms** for legacy and **783 ms** for canary, making canary about **23% slower** at p95. The normal case is similar, while the canary tail is worse; the required 20% p95 gain is not met. This local comparison does not cover provider CDNs or Safari. The fixture build opts into only `http://127-0-0-1.nip.io:18560` through `NEXT_PUBLIC_PLAYBACK_FIXTURE=1`; keep that flag unset in ordinary and deployed builds.

Three additional Windows Chrome batches per core (54 warm samples each) produced p50 **603 ms legacy / 591 ms canary** and nearest-rank p95 **1,200 ms legacy / 1,300 ms canary**. A single latest 18-sample batch pair swung the other way (p95 1,200 ms / 814 ms), while an earlier batch had a canary p95 of 2,251 ms. Paired phase capture shows startup and load-to-frame tails vary substantially between runs; no repeatable ≥20% p95 gain is established. The benchmark now records each sample's navigation-to-frame, load-start, and load-start-to-frame timings together, and its core label can be supplied with `PLAYBACK_BENCHMARK_CORE`.

A fresh optimized standalone rebuild on 2026-09-28, with the fixture API URL baked into both builds, produced three more Windows Chrome batches per core (54 warm samples each). Pooled p50 was **564 ms legacy / 561 ms canary**; nearest-rank p95 was **924 ms legacy / 832 ms canary**, a 10% canary improvement. Per-batch p95 varied: **2,388 / 752 / 962 ms legacy** and **999 / 1,088 / 700 ms canary**. The 2,388 ms legacy outlier spent 1,725 ms between media `loadstart` and the decoded frame; the other batches did not reproduce it. Typical startup is effectively unchanged and the pooled gain is below the required 20%, so the cutover gate remains open. This fixture comparison does not establish external-provider performance or Safari behavior.

A further fresh optimized standalone comparison on 2026-09-28 alternated three batches per core (54 warm samples each) against the same local fixture. Pooled p50 was **554 ms legacy / 561 ms canary**; nearest-rank p95 was **1,001 ms legacy / 781 ms canary**, a **22% pooled canary improvement**. Batch navigation p95s were **1,126 / 817 / 2,051 ms legacy** and **988 / 710 / 1,217 ms canary**: canary was faster in each pair, but only the third pair exceeded 20%. The pooled result meets the numeric threshold; the size varies by batch, so repeat on a stable runner before rollout. Paired `loadstart`-to-frame p95 was 345 ms legacy / 316 ms canary, while that phase's p50 was 134 / 148 ms. This local fixture does not establish external-provider performance.

A final-code remeasure after the playback-rate ownership change alternated three more batches per core on 2026-09-28 (54 warm samples each; 114 total warm starts reached a frame). Pooled p50 was **576.5 ms legacy / 540.5 ms canary**; nearest-rank p95 was **888 ms legacy / 852 ms canary**, only a **4% pooled improvement**. Paired batch p95s were **1,531 / 930 / 811 ms legacy** and **1,325 / 680 / 877 ms canary**. The canary improved the first two pairs by 13% and 27%, then was 8% slower in the third. Pooled load-start p95 was 716 ms legacy / 664 ms canary, and load-start-to-frame p95 was 236 / 220 ms. The result does not meet the 20% cutover gate; keep legacy as default and repeat on a stable runner. The large tail moved between startup and media phases, reinforcing that local Windows timings remain sensitive to runner noise.

A current-branch optimized standalone comparison on 2026-09-28 alternated three batches per core (54 warm samples each; all 108 warm starts reached a decoded frame). Pooled p50 was **559 ms legacy / 510 ms canary**; nearest-rank p95 was **995 ms legacy / 854 ms canary**, a **14% improvement**. Batch p95s were **1,278 / 773 / 746 ms legacy** and **818 / 796 / 1,745 ms canary**; the largest canary tail occurred before media `loadstart`, while the largest legacy tail occurred after it. Pooled p95 was **731 / 676 ms navigation-to-loadstart** and **256 / 218 ms loadstart-to-frame**. This build still included the redundant browser session bootstrap on Watch, which has since been removed. It does not meet the 20% cutover gate or verify Safari/provider-CDN performance.

After suppressing the redundant root `/v1/me` request on server-seeded Watch routes, one fresh optimized batch per core on 2026-09-28 reached a decoded frame in all 18 warm starts. Legacy p50/p95 was **375 / 791 ms**; canary was **483 / 2,154 ms**. The maximum canary sample spent **2,060 ms before `loadstart`** and 94 ms reaching a frame afterward; the maximum legacy sample spent 391 ms after `loadstart`. The run also logged fixture telemetry proxy `ECONNRESET` errors. A first canary attempt exposed an autoplay race in the benchmark's Play-button check; that check now tolerates playback starting before the assertion and the rerun passed. These sequential single-batch results are runner-sensitive and inconclusive, so they do not change the 20% gate. Repeat alternating batches on a quiet runner and verify macOS/iOS Safari HLS before rollout.

The canary controller reports `started` after `requestVideoFrameCallback` confirms a decoded frame where supported. Browsers without that API fall back to the media element's `playing` event. A 12-second startup watchdog sends an unrendered source through failure and fallback instead of recording a false successful start.

Windows Playwright WebKit passes hydration and subtitle discovery with the canary. The repeated short-lease test originally paused before its assertion on both cores. Instrumentation showed native source replacement reset playback speed, letting the 30-second fixture end while slow browser setup ran. The player now sends selected speed changes directly to both controller cores; controllers restore that preference after metadata, `canplay`, successful play, and WebKit's delayed seek-settle checks. The focused test pauses the fixture during setup, then verifies member-selected speed, playing intent, caption, and paused position across two renewals. It passes on both optimized cores in Windows Chrome and WebKit. The native engine also no longer inserts an empty `video.load()` between removing `src` and assigning the renewed URL, which had stranded WebKit's resource loader. Actual macOS/iOS Safari HLS, real DASH decoding, and live-provider first frames remain outstanding.

Cutover remains gated on a measured controlled-fixture first-frame p95 improvement of at least 20%, no canary regression in startup success, buffering, fatal errors, or recovery, and macOS/iOS Safari HLS verification. Route a small cohort to a separate `next` web deployment at the edge only after local release gates pass; changing the environment value back to `legacy` restores the prior controller. Do not retire the prior path before those gates pass.

## Configured-provider audit

[The per-adapter static audit](./provider-rebuild-audit.json) covers 62 configured rows, 49 adapter identities, and 35 enabled rows in the latest `infra/playback/providers.local.json` snapshot. Thirty-two adapter identities have at least one enabled row; only VixSrc has controlled browser-playback evidence, leaving 31 enabled adapter identities unverified in browser playback. The audit does not establish provider permission. All scanned adapters use the SDK result boundary and explicit access deadlines; none calls global `fetch` or executes provider-supplied code at runtime. Aphrodite still imports an opaque vendored signing chunk; its provenance, checksum, and isolated fixture remain a deployment review item. API transport applies DNS-pinned destinations and body limits; `validatedSources` applies media-host and HTTPS checks; resolver attempts are bounded and repeated viewer failures cool down a provider.

The scan cannot prove a provider has permission to serve media, that its current CDN supports browser CORS/codecs, or that a source reaches first frame. VixSrc has a controlled end-to-end HLS fixture; deterministic contract coverage varies across the other adapters, and each needs source-specific browser evidence before claiming playback health. The disabled VidSrc adapter now rejects encrypted responses that previously required executing provider-supplied WASM. Keep it disabled until a native bounded decoder and fixture exist.

## Local verification

`bun run check` passed lint, type checking, 877 unit and integration tests across all six workspaces, and optimized API, web, and Worker builds on 2026-09-28. `bun run infra:validate` passed both Compose configurations and Terraform format, init, and validation. Focused Chromium and Windows WebKit fixtures cover native resume, direct HLS decoding, unavailable-source fallback, renewal, hydration, and keyboard focus retention. The final-code local pooled performance result is 4% better at p95 and does not meet the 20% gate; a stable-runner repeat, macOS/iOS Safari HLS, and live-provider first frames remain open.

On 2026-09-28, one web screen test exceeded Vitest's five-second default under full-suite load but passed in isolation. The web jsdom timeout is now 10 seconds; its 48-file rerun passed 255/255, and the root `bun run check` subsequently passed.
