## Context

Direct provider URLs can fail in production because source lookup runs from the API host, while browser delivery comes from each member's network. Local success therefore does not establish production lookup or browser playback. CORS, referer requirements, upstream IP blocking, and egress-bound links are separate provider constraints. The API's existing scheduler must continue to own provider order, health, sessions, Admin configuration, and source validation.

## Decision

Separate Cloudflare Resolver and Media Relay deployments. The Resolver Worker executes exactly one API-selected provider attempt per authenticated request. Its request contains the adapter identifier, validated current provider row, playback reference, region/language, and canonical metadata prepared by the API. The Worker uses only compiled adapter implementations, bounded HTTP transport, and a bounded host scope derived from the API's validated configuration. It does not accept arbitrary caller URLs, own fallback ordering, or receive TMDB credentials. Every source is validated again against the current API provider registration before it can become a session.

Keep media delivery ordered Direct → Cloudflare Relay → Embed. Direct media and its segments flow from the browser to the provider. A distinct Media Relay Worker accepts short-lived signed grants for explicitly configured relay rows and is enabled only after that row passes end-to-end browser playback, manifest, segment, seek, caption, and cross-Worker egress checks. Worker separation does not imply shared upstream egress.

Do not use OVH for generic provider lookup fallback or media relay. If a Cloudflare resolution attempt fails, the API proceeds through its existing provider scheduler, then configured Embed, then unavailable. Do not enable paid Cloudflare usage automatically.

## Consequences

CookieBakers remains in the configured Direct waterfall even while its circuit is degraded, because its upstream route is known to flap and often recovers on the next request. This provider-scoped cooldown exception does not bypass its concurrency, per-minute request, or resolver deadline limits; the health indicator still reports recent failures.

The 2026-10-12 repair adds bounded per-provider Resolver and Media Relay origin maps. Only one configured origin is invoked for an attempt; a regional failure does not trigger a second regional or API lookup. AnimeKitsu, Evion, Rigel and AnimeKai use the Europe Resolver; Aphrodite uses the default Resolver. Rigel, AnimeKai, Mirage and Aphrodite use the separate Europe Media Relay after measured browser acceptance. Its placement hint does not guarantee a particular country or a common upstream IP. The Aphrodite route demonstrates why resolver and media egress must be tested together: the default Media Worker returned 403, while the Europe route passed. Other Admin fields and disabled/removed rows retain their settings.

AnimeKai's proof calculation exceeded the Free Worker's CPU budget. Only that pure calculation is delegated to the existing API using a separate secret and fixed authenticated endpoint. It accepts a bounded nonce and difficulty, runs at most two credential-free child processes for eight seconds, and executes only compiled code. It accepts no URLs or provider scripts and performs no provider lookup or media transfer. The Worker retains all provider HTTP calls, accounts for the callback as a subrequest, refuses redirects, bounds the response, and treats timeout or capacity failure as a failed provider attempt. This is API control-plane computation, not an OVH resolution fallback. Disabling the helper returns AnimeKai to its local solver and its previous CPU-capacity risk.

Rigel's large playlists also exceeded Worker CPU during signing. An authenticated Media Worker control endpoint accepts only an existing approved Rigel HLS grant and fetches a raw playlist up to 2 MB. The API independently checks its base and every reference and compiles the bounded graph (up to 6000 references). Child playlists retain the API control route; segments, maps and keys use the configured Cloudflare Media Relay. No Rigel upstream fetch moves to OVH. Other providers keep their existing graph limits. Seeking gets a separate 30-second deadline while ordinary playback stall limits remain unchanged.

One successful Direct resolution attempt uses one incoming Resolver Worker request; each Worker fallback attempt uses another. The reviewed Miami Relay lookup exception does not invoke the Resolver Worker. API metadata lookups remain in the API and do not send credentials to Cloudflare. Direct playback does not consume Media Relay requests for manifests or segments. Each relayed manifest, segment, key, or map request invokes the Media Relay Worker and contributes to its account usage; approved discovery routes serve compiled control playlists through the API. Provider availability still depends on upstream Cloudflare reachability and the Worker plan's per-invocation limits; this design cannot make blocked providers available by itself.

The Worker accepts live Admin edits without redeployment because the API supplies the current validated row on each attempt. The API remains the trust boundary for that configuration and independently validates Worker output. A malformed, oversized, timed-out, over-scope, or capacity-limited attempt is a provider failure and cannot select or redirect to an arbitrary destination.
