## Activate a limited permitted trial

The current API PLAYBACK_RELAY_PROVIDERS and Worker RELAY_PROVIDERS maps approve Megavid, 9Anime (hd-2 only), Anixo, Zoko and AniWave for anime; BingeBang YMovies, Storm Boron, Zeta, Rive Nebula, Rive Zephyr, WeCollege Miami, WeCollege Boise and StigStream for movies and TV. All thirteen are configured locally as Video source with deliveryMode: relay, including both WeCollege rows by explicit owner choice. Vidnest and VaPlayer stay browser-direct: their shared media host answers residential direct fetches with CORS-open manifests yet returns 403 to Cloudflare Worker egress, so relaying them surfaces as `headers` browser failures. Durable Admin overrides determine enabled state; Boise is currently disabled. Durable settings preserve existing order. Examples keep these rows disabled. Vixsrc stays direct-only. To add another relay provider, configure its base row with deliveryMode: relay, then explicitly add reviewed exact hosts to both policies. Missing deliveryMode defaults to direct. A direct provider is never enrolled merely because it has approved media hosts or because browser playback fails. Wildcards/regexes are never expanded automatically. The Free Worker is deployed and enabled. Upstream resolution alone does not establish edge compatibility: see the provider integration audit for sampled delivery successes and failures. Failed relay playback continues through the relay pool; embed and P2P remain deferred.

For the current trial, deploy with `wrangler deploy --config infra/cloudflare/media-relay.local.jsonc`; the checked-in `media-relay.wrangler.jsonc` intentionally stays disabled and has example values. The active local API settings live in `apps/api/.env`. Apply them with the current Docker overlays using `docker compose -f compose.yaml -f compose.dev.yaml -f compose.playback.yaml --profile playback up -d --no-deps --no-build api` after building the source image; rebuild/recreate the optimized web service after browser changes. The dev overlay mounts the relay workspace, and gateway playback routes have the longer recovery timeout.

1. Review upstream permission, region and public-domain ownership for one explicitly declared relay provider. Keep several direct providers available so direct recovery is tried first. Do not use this mechanism to bypass provider access controls. Use owned fixture media for the first staging check.
2. Set `APP_ORIGIN` in `infra/cloudflare/media-relay.wrangler.jsonc` to the exact Consumit browser origin. Set `RELAY_PROVIDERS` to a JSON map from configured provider id to **exact** approved public media hosts. Include the root, variants, audio, keys, maps and segment hosts; neither wildcard hosts nor regexes are accepted here. The API separately checks these hosts against the existing configured provider allowlist. No provider is approved merely because its adapter exists.
3. For this trial use Workers Free and omit limits.cpu_ms, which Free does not support. Upgrade only if the owner later authorizes Paid. Add a high-entropy secret of at least 32 characters as the Worker's `RELAY_SECRET` using Wrangler secret storage. Supply the identical value privately as API `PLAYBACK_RELAY_SECRET`. Never commit it. Keep full request URLs, encrypted capability paths and upstream URLs out of logs and analytics.
4. Deploy the Worker configuration with `RELAY_ENABLED=false`, inspect the deployment's exact HTTPS origin, then set API `PLAYBACK_RELAY_ORIGIN` to it. Set API `PLAYBACK_RELAY_PROVIDERS` to the same approved map, `PLAYBACK_RELAY_ENABLED=true`, and retain `PLAYBACK_ENABLED=true`. Restart/redeploy the API and rebuild the web bundle so its shared contract accepts `delivery: relay`. The Docker dependency stages include the new shared package.
5. Enable the Worker only for the approved trial. Check direct startup, simulated browser CORS failure → remaining direct providers → relay first frame, nested variant/audio/key/map fetching, seeks/ranges, expiry renewal, and Worker outage → next relay candidate → honest unavailable state. Verify frame advance and real seeking in desktop Chrome and native-HLS Safari. Check separate-audio cancellation and captions across the transition. The production Worker runtime, upstream permission and actual delivery still require these staging checks; unit tests do not establish them.
6. Free enforces 10 ms CPU per invocation and an account-wide 100,000-request UTC daily quota. Monitor CPU-limit errors and quota usage; exceeding either can interrupt relay. If later upgraded to Paid, start with limits.cpu_ms: 50 and adjust only after measurement. Disable the Worker with `RELAY_ENABLED=false` to stop video relay immediately; existing sessions can exhaust the relay tier and show unavailable; a fresh session restarts direct while the API still retains its grant configuration. Disabling/removing API relay configuration invalidates existing relay sessions and requires fresh playback. Removing a host/provider in the Worker policy also denies previously issued capabilities. Rotate the shared secret on both sides to invalidate all grants.

Grant expiry is capped at 30 minutes and by upstream expiry; owned sessions can renew after the media capability expires. Redirects are manual, capped at three, and checked at every hop. Header hints stay on their original media host except the fixed Zoko recipe: hls.dramahot.top may reference independently approved hls1.drama1.cfd, which receives only the recorded public zokoanime.video Referer/Origin. HTTP credentials, arbitrary URL query overrides, arbitrary byte transforms, playlist variables, content steering and multi-range requests fail closed. Binary responses stream with backpressure and a 15-second stalled-read deadline; resolution headers/manifests have a 10-second deadline. The API never receives media segments. DASH and optional separate audio continue browser-direct. Provider iframe fallback remains a future product/adapter decision.

## Seven-day measurement

Enable the existing OTEL exporter/collector and retain at least seven days of Prometheus samples. The new `playback.viewing.duration` counter counts **observed advancing local playback wall time** by `delivery`; playback rate does not inflate hours. Pauses, seeks and stalls reset/exclude samples, background gaps are capped at five seconds, and telemetry is best-effort. Casting is outside this initial measurement. Use delivery tags carried in each event so queued events do not inherit the next source's delivery. This is a conservative operational estimate, not a billing ledger or an exact audience count.

With the existing collector namespace, inspect the exported counter as `consumit_playback_viewing_duration_seconds_total` (confirm its name in your collector). Direct and relay hours are `sum by (delivery) (increase(consumit_playback_viewing_duration_seconds_total[7d])) / 3600`. Relay share is relay seconds divided by all measured viewing seconds. Existing `consumit_playback_client_duration_milliseconds_bucket` histograms provide startup (`event="started"`) and buffering (`event="buffer-end"`) distributions, filtered by delivery. Existing source-selection and recovery counters show route changes and failures. Check that direct → next direct → relay and relay → next relay all attach immediately at retained position and play intent.

Cloudflare dashboard metrics provide **all** incoming Worker requests, errors, CPU time and exceeded limits. Custom `relay.request` logs contain only provider, manifest/media category, status, response bytes and wall duration. They never contain tokens, URLs or member identity. Log sampling is 1%; bytes from sampled logs are diagnostic estimates, while billing/request/CPU totals must come from account metrics. Wall duration is not CPU time. Disable unsampled access-URL exports. Browser telemetry loss and manifest/audio/retry traffic mean segment count estimates cannot replace billed totals.

Record one daily row with direct hours, relay hours/share, Worker request count, CPU milliseconds, errors/CPU-limit errors, p50/p95 startup, p50/p95 buffer duration, estimated streamed bytes and projected monthly spend. Compare the same provider/browser/region cohorts against direct playback. Stop or roll back if failures, startup, buffering, CPU-limit errors or spending regress beyond the operator's preselected trial budget. After seven days, expand only if permitted traffic plays reliably and observed costs fit that budget. Full-episode soaks and Safari/native-HLS checks are required before claiming production delivery compatibility.

## Plan limits and pricing hypothesis (verified 2026-10-03)

The active account remains on [Workers Free](https://developers.cloudflare.com/workers/platform/limits/): 100,000 requests per account per day, reset at midnight UTC, and 10 ms CPU per invocation. These are shared account limits, not a Consumit allocation. Daily quota exhaustion returns Cloudflare error 1027; exceeded CPU may return error 1102. Media and playlist requests both consume quota. At six-second segments, 100,000 segment requests represent at most roughly 167 viewing hours/day before playlists, audio, retries and other account Workers; this is arithmetic, not a capacity promise. Large VOD manifests may exceed the CPU limit even when media streaming works. Paid pricing below is a future scaling comparison.

[Cloudflare Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) lists a $5/month minimum, 10 million included requests, $0.30 per additional million requests, 30 million included CPU milliseconds and $0.02 per additional million CPU milliseconds, with no separate data-transfer or bandwidth charge. Account-wide included usage may already be consumed by other Workers. Request-only projections for 1.2 billion / 240 million / 120 million / 12 million requests are $362 / $74 / $38 / $5.60; they exclude CPU, logs, playlists/audio/retries and upstream costs.

Calculate measured Worker cost as `5 + max(0, monthly_requests - 10e6) / 1e6 * 0.30 + max(0, monthly_cpu_ms - 30e6) / 1e6 * 0.02`, then add all other actual charges. [Cloudflare's Developer Platform terms](https://www.cloudflare.com/service-specific-terms-developer-platform/) permit temporary request/storage limits for network burden; cheap published prices do not certify petabyte-scale relay acceptance. Ordinary CDN caching is a separate service/policy and is not enabled by this trial.

Only after this baseline should a separate P2P experiment compare one popular, identical permitted stream, matched renditions, peer availability, startup/buffering, bytes offloaded, device resource use and consent behavior. Ship P2P only if measured savings outweigh its operating and product costs.
